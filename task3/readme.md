# Анализ текущей архитектуры и риски при росте нагрузки

## Текущее состояние
- `ins-product-aggregator` синхронно опрашивает 5 страховых компаний при каждом вызове, агрегирует данные и возвращает ответ.  
- `core-app` запрашивает продукты раз в 15 минут, `ins-comp-settlement` — раз в сутки.  
- `ins-comp-settlement` раз в сутки вызывает REST API `core-app` для получения списка оформленных страховок.  
- Оба сервиса хранят локальные реплики данных о продуктах и тарифах.

## Планируемые изменения
- Подключение ещё 5 страховых компаний (всего 10).  
- Ожидается рост интенсивности запросов и объёмов данных.

## Проблемы и риски

### 1. Увеличение задержки и вероятности сбоев при синхронной агрегации
Синхронный опрос 10 внешних API значительно увеличит время ответа `ins-product-aggregator`. Частичный отказ одной компании может привести к тайм-ауту всего запроса или возврату неполных данных.

### 2. Зависимость от доступности внешних систем
Ошибка или задержка одной страховой компании напрямую влияет на обновление продуктов в `core-app` и `ins-comp-settlement`. При росте числа партнёров эта проблема усугубляется.

### 3. Жёсткая временная связь между сервисами (point-to-point)
- `ins-comp-settlement` ежесуточно опрашивает `core-app` для получения оформленных страховок. При недоступности `core-app` реестр не формируется, данные могут быть потеряны до следующего окна.  
- Периодические запросы продуктов создают интервал неактуальности (до 15 минут для `core-app` и до суток для `settlement`).

### 4. Потеря данных при сбоях во время обмена
Если `ins-comp-settlement` упал во время выполнения запроса к `core-app`, оформленные за день страховки могут не попасть в расчёт. Аналогично, при ошибке синхронной публикации событий (если бы она использовалась) без гарантий доставки возможны пропуски.

### 5. Масштабирование и мониторинг
Синхронные цепочки вызовов сложнее масштабировать и отлаживать. Рост числа компаний требует вертикального масштабирования `aggregator` и увеличивает «радиус взрыва» при инцидентах.

### 6. Невозможность независимого обновления данных
Локальные реплики обновляются только по расписанию, поэтому информация о новых продуктах появляется с задержкой. При частых изменениях тарифов это может приводить к некорректным расчётам.

## Предлагаемые решения
1. **Переход на асинхронное обновление продуктов через Event-Streaming**  
   - `ins-product-aggregator` будет фоново опрашивать страховые компании и публиковать изменения в топик Kafka `product-updates`.  
   - `core-app` и `ins-comp-settlement` подписываются на этот топик и обновляют свои локальные реплики в реальном времени.  
   - При ошибке опроса отдельной компании данные можно повторить, не затрагивая остальные.

2. **Публикация событий о новых страховках через Kafka**  
   - `core-app` при оформлении полиса публикует событие `policy-issued` в Kafka.  
   - `ins-comp-settlement` потребляет этот топик, избавляясь от необходимости синхронного вызова REST.  
   - Гарантия доставки обеспечивается сохранением сообщений в Kafka и повторной обработкой при сбоях.

3. **Использование паттерна Transactional Outbox**  
   - В рамках одной транзакции `core-app` записывает оформленный полис в свою БД и помещает запись в outbox-таблицу.  
   - Специальный процесс (Debezium) читает outbox и публикует события в Kafka.  
   - Это исключает рассинхронизацию между состоянием БД и отправкой события.

4. **Постепенное внедрение**  
   - Сохраняется обратная совместимость: `ins-comp-settlement` может продолжать использовать REST, пока не будет готов к потреблению из Kafka.  
   - `ins-product-aggregator` параллельно с публикацией в Kafka может оставить синхронный API для плавного перехода.
