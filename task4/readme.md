# Задание 4. Проектирование продажи ОСАГО

## Реализация osago-aggregator

**Хранилище данных:** 
Сервис управляет жизненным циклом каждой заявки: идентификатор, статус, список страховых компаний, временные метки, полученные предложения. Для надёжной обработки при перезапусках и горизонтальном масштабировании предлагается использовать собственную БД (PostgreSQL)

**API, предоставляемый core-app:**
1. POST /applications – создать новую заявку, возвращает applicationId
2. Дополнительно может предоставлять GET /applications/{id} для получения текущего статуса, но основная доставка предложений происходит асинхронно.

## Интеграция core-app - osago-aggregator

Используется гибридный подход:
1. REST – для синхронного создания заявки
2. Event-Streaming (Kafka) – для асинхронной доставки предложений. osago-aggregator по мере получения ответов от страховых компаний публикует события в топик. core-app подписан на этот топик и ретранслирует данные пользователю.

Такой подход сохраняет событийно-ориентированную архитектуру из задания 3 и позволяет масштабировать оба сервиса независимо

## API для веб-приложения и интеграция с фронтендом
1. REST остаётся для инициирования заявки (POST /osago/applications) и загрузки исторических данных
2. Для отображения предложений по мере поступления используется WebSocket. core-app после создания заявки возвращает идентификатор, а браузер открывает WebSocket, через который core-app отправляет каждое новое предложение сразу после получения из Kafka.

## Паттерны отказоустойчивости
Для интеграции нового сервиса с внешними страховыми компаниями предлагается использовать:
1. Timeout (60 с) - чтобы исключать долгие зависания 
2. Retry - повторные попытки при временных сетевых ошибках (с экспоненциальной задержкой)
3. Circuit Breaker - предотвращает каскадные сбои при длительной недоступности одной из СК

В рамках интеграции core-app -> osago-aggregator (REST) предлагается использовать:
1. Rate Limiting - защита агрегатора от лавины запросов при пиковой нагрузке 
2. Timeout (5 с) - колроткий тайм-аут для синхронного создания заявки

## Работа в среде с несколькими инстансами
При горизонтальном масштабировании core-app каждый экземпляр подписывается на Kafka с уникальной consumer group. Это гарантирует, что событие о предложении будет доставлено всем экземплярам, и тот, у которого открыто WebSocket-соединение с нужным пользователем, отправит данные клиенту
